Nonprofit Expansion Decision System

Power Apps · SharePoint Lists · Governance by design

The problem

A growing nonprofit wants to expand into new markets, but "are we ready?" was a judgment call made in conversation. Leadership needed the answer to come from evidence: a market opens only when the organization's finances and production capacity meet set criteria, that market's own entry requirements are satisfied, and a formal vote approves the move. My job, as GRC Chair, was to design and build the system that makes that decision — and makes it auditable.

How it works

  • Criteria come in four families — Financial, Production, Market-entry, and Success-metric — all stored in a single Criteria list, separated by a Family field rather than four parallel lists, so one pattern serves every family.
  • Each criterion has a form: a numeric threshold ("ticket backlog at most 25"), a yes/no condition ("insurance policy current"), or a sustained-for rule ("operating reserve of at least $10,000, held for one quarter").
  • Values are snapshots. A separate values store holds dated observations for each criterion, entered by hand from verified sources. The app never calculates from live systems; it reads the snapshot record and renders a verdict — met, or not met.
  • Sustained-for has a precise boundary: a snapshot exactly one duration old belongs to the prior period, so a value must be strictly inside the window to count.
  • Markets move through stages — Idea → Plan → Waiting or Goal → Progressing → Ready → Approved → Executed. A single gate review covers the financial, production, and market-entry sides together; approval requires a recorded board/founders vote, planning approvals run departmental-then-board, and every plan carries my GRC sign-off. The stage field is adjusted only after a vote concludes.
  • Approved is not the end. An executed market is later judged against the fourth family — success metrics — and can return to Waiting if it stops meeting them.

What is built

The data layer is eight SharePoint lists: Departments, Criteria, the values store, Markets, Regulations, Cost lines, Document check-offs, and Approvals — built with standard connectors only. On top of it, the organization's dashboard gallery reads the org-level criteria and renders a live verdict per criterion, with headline counts computed from the data itself: Financial: 2 of 2 met · Production: 1 of 3 met.

The core logic was proven before any interface work: a sustained-for financial criterion with four monthly snapshots (8,500 → 10,200 → 10,800 → 11,500 against a 10,000 threshold held for one quarter) evaluates to MET, and the boundary rule was tested deliberately, not assumed.

What I learned building it

  • Verdict rendering differs by criterion form, so the interface stacks one verdict label per form, each visible only for its own form — simpler and more reliable than one mega-formula.
  • Lookups and nested filters need values captured as scalars before filtering; scope in this environment does not behave the way a programmer first expects.
  • Design rule I now reuse everywhere: if a field's values are a closed set, it is a choice field; if the app branches on it, the choices are locked; quantities are always numbers.
