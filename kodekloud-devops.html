Day 3 — Secure Root SSH Access

Completed November 12, 2026

xFusionCorp security protocol: disable direct SSH root login on all three app servers (stapp01, stapp02, stapp03).

Step by step:

  1. On each server, check PermitRootLogin in /etc/ssh/sshd_config (it was yes).
  2. Change it with sed: sudo sed -i 's/^PermitRootLogin yes/PermitRootLogin no/' /etc/ssh/sshd_config.
  3. Verify the config now shows PermitRootLogin no.
  4. Restart the SSH service: sudo systemctl restart sshd.
  5. Verify the effective setting: sudo sshd -T | grep -i permitrootlogin returns permitrootlogin no.

Day 4 — Script Execution Permissions

Completed November 14, 2026

The backup script /tmp/xfusioncorp.sh on App Server 1 had no permissions at all; grant execute access so any user can run it.

Step by step:

  1. Read the starting state with ls -l: ---------- — ten dashes, no permissions for anyone; the file is owned by root, so the fix needs sudo.
  2. Assemble and run: sudo chmod 755 /tmp/xfusioncorp.sh.
  3. Verify the end state: -rwxr-xr-x — owner rwx, group r-x, others r-x.

What it taught: The 4-2-1 scheme: r = 4, w = 2, x = 1; each group's sum is one digit of the mode, so rwxr-xr-x = 755. A script also needs read permission — bash has to read the file to run it.

Day 5 — SELinux Installation and Configuration

Completed November 15, 2026

App Server 2 (stapp02): install the SELinux packages and permanently disable SELinux ahead of later configuration work; the graded state is the config file, not the current runtime status.

Step by step:

  1. Check the starting state: /etc/selinux/config doesn't exist yet, and rpm -qa | grep -i selinux shows only the libselinux libraries — the policy and tools aren't installed.
  2. Install: sudo yum install -y selinux-policy selinux-policy-targeted policycoreutils policycoreutils-python-utils. The config file now exists, reading SELINUX=enforcing.
  3. Change it permanently: sudo sed -i 's/^SELINUX=enforcing/SELINUX=disabled/' /etc/selinux/config.
  4. Verify: the config reads SELINUX=disabled; SELINUXTYPE=targeted left untouched.

What it taught: The config file is what the kernel reads at boot — editing it is the permanent change. setenforce 0 only affects the running system until reboot. A missing config file is itself diagnostic: it arrives with the policy packages.

Day 6 — Create a Cron Job

Completed November 16, 2026

On all three Stratos app servers: install the cron package, start the service, and add a root cron job that writes to /tmp/cron_text every five minutes.

Step by step:

  1. Install the package: sudo yum install -y cronie.
  2. Start the service: sudo systemctl start crond — verified active (running).
  3. Check root's existing crontab first: sudo crontab -u root -l (all three servers: no crontab — a clean slate).
  4. Install the entry: echo '*/5 * * * * echo hello > /tmp/cron_text' | sudo crontab -u root -.
  5. Verify by listing root's crontab and seeing the line. (Server 1 worked step by step; servers 2 and 3 done solo with the same routine.)

What it taught: Package vs service: cronie is the package, crond is the daemon it provides. Cron fields are minute, hour, day-of-month, month, day-of-week — */5 in the minute field means every five minutes.

Day 7 — Linux SSH Authentication

Completed November 18, 2026

Set up password-less SSH from the jump host (user thor) to all three app servers, so scheduled scripts can run unattended.

Step by step:

  1. Check ~/.ssh on the jump host first: no existing key pair, so no overwrite risk.
  2. Generate an ed25519 key pair with ssh-keygen — default location, empty passphrase.
  3. Distribute the public key with ssh-copy-id to tony (stapp01), steve (stapp02), and banner (stapp03) — each asks for that user's password one last time.
  4. Verify: SSH into each server with no password prompt. (Servers 2 and 3 done solo with the same routine.)

What it taught: The public key is the lock — it's built to be shared and lands in each target's authorized_keys. The private key never leaves the machine that generated it. The empty passphrase is the point: unattended scripts have no human to type one.

Day 9 — MariaDB Troubleshooting

Completed November 24, 2026

The Nautilus app can't connect to its database — the MariaDB service is down on stdb01. Diagnose and fix it.

Step by step:

  1. Check the service: loaded, disabled, inactive (dead) — it hadn't crashed; it was off and not set to start at boot.
  2. First start attempt fails. The status log names it: "Database MariaDB is not initialized… Make sure the /var/lib/mysql is empty."
  3. Look for /var/lib/mysql: it doesn't exist. Listing /var/lib shows why — the data directory had been renamed to /var/lib/mysqld (the giveaway: owned by mysql:mysql).
  4. Rename it back: sudo mv /var/lib/mysqld /var/lib/mysql. The restored directory is empty with the right owner — exactly the state the startup script needs.
  5. Start again: the service comes up active (running) and enabled.

What it taught: start means now; enable means every boot. And "preset: disabled" in the status output is just the vendor's shipped default — the operative word is the first one, enabled.
